The signal arm has still never opened a position

Every prediction on record sits between 30% and 40% confidence against a 65% gate, so scan() returns zero candidates before constructing a single vertical, while the control arm sells a spread a day regardless. That has not changed. What changed today is why it might be happening.

The 09:03 edition listed three candidate explanations. One is now eliminated. “The corpus was too thin to support conviction” no longer holds: the 09:55 cycle ran on a properly diversified prompt — 24 macro, 15 news, 1 YouTube — and returned 34%, statistically indistinguishable from the lopsided cycles before it.

Two remain. Either the tape has genuinely been unattractive throughout the measurement window, or confidence_dir_scale compresses conviction so that 65% is unreachable in practice. The 09:55 rationale argues for the first: it calls the setup a “two-sided gap window rather than a clean premium-selling setup” and says “size down or stand aside”. That is a model declining to have a view, with reasons, rather than one failing to form one.

Answered, 2 August — and neither candidate was right. The session ran untouched and confidence moved (0.32–0.42, no two consecutive cycles alike), so the corpus was suppressing variance. But the level never approached the gate, and 199 hand labels explain why: 188 of 199 items carried no directional sign at all, and 70 of the 81 judged relevant were still zero. The gate asks how sure the model is of a direction that the inputs do not contain. No scorer and no model fixes that — Sonnet 5 was tried and its weighted error landed inside the 1.3% run-to-run noise floor.

4 August — a third explanation, and this one is measurable. The gate is a fixed threshold on a number whose scale changed underneath it. Split the 180 predictions on the day the synthesis aggregator replaced the weighted mean and they are plainly two different distributions:

AggregatorWindownConfidence rangeMeanCleared 0.65
weighted mean24–28 Jul1390.30–0.6580.562 (1.4%)

The mean aggregator sat in a compressed band and grazed the gate twice in 139 predictions — 0.65 was already a near-dead threshold, which is why no signal trade had ever opened even before the swap. Synthesis then reported genuinely differentiated but systematically lower conviction and the gate became unreachable outright. Nothing re-derived the threshold when the scale moved, and nothing alarmed: a gate that blocks every cycle looks identical in the logs to a market that never qualifies.

Recalibrated to 0.40 — the 75th percentile of the synthesis distribution, so the gate keeps its intended meaning (trade the upper quartile of conviction) on the scale now in use. Against the 41 cycles on record it admits 15, and against today's session 5 of 9. Provisional: 41 observations across seven sessions of one calm, contango, IV-under-RV regime.

This does not retire the gate, and the item below still stands: at 0.40 the directional check still runs before _sides_allowed(), so the condor is reachable on ~37% of cycles instead of 0% rather than being decided on its merits. Nor does it touch the deeper finding above — the inputs still mostly carry no directional sign. What it fixes is the gate being the binding constraint, which it should never have been.

Close conditiona cycle logging num_candidates > 0, and a first arm='model' row in paper_positions. Neither has ever occurred. If the arm still does not trade at 0.40, the blocker is downstream — edge, POP, RoR or liquidity — and is a different investigation.

The confidence gate makes the iron condor unreachable

was 100% of cycles · now ~63% found 2 Aug · eased 4 Aug

Partially relieved, not fixed. The 4 Aug recalibration to 0.40 means the gate no longer exits on every cycle, so a condor can now be constructed on roughly 37% of them. The ordering problem below is untouched: the directional check still runs first, so on the other ~63% the condor is still rejected for having no directional view. Lowering the threshold changed how often the wrong question is asked, not which question it is.

_candidates() checks directional confidence and returns an empty list before it ever consults _sides_allowed() or builds a condor:

Order in _candidates()GateReached?
1confidence < 0.65 → return []exits here, every cycle
2_sides_allowed() per-tail checknever reached

The condor is the instrument for “no directional view, both tails quiet”. The code builds it; the gate above rejects the trade for having no directional view. The scanner declines condors on precisely the grounds that make a condor correct. _sides_allowed() already says so in its own docstring — “flat with both tails quiet is the best setup a premium seller gets” — so the reasoning was fixed one layer down and the gate above it was left alone. Sopana reached the same conclusion independently: when its directional votes fail to clear it sells a condor rather than standing aside.

The tail gate that should be deciding this has passed 18 of 18 cycles — downside 36–48%, upside 20–32%, against a 55% cap, zero breaches. Every prediction on record already says no adverse move is detected.

Actmove the directional check so it filters verticals only, leaving condors to the tail gate, min_edge_score and the new premium-richness terms. The close condition is simple and has never once been met: a cycle logging num_candidates > 0.

The severe part is second-order. manage() hits continue on an unmarkable position before it evaluates the exits, so such a position is not merely unpriced — it is unclosable. The scanner is dying mid-cycle on a native heap abort

diagnosed & fixed 3 Aug watching: 0 / 10 clean days

Roughly one invocation in eighteen dies with glibc's double free or corruption and Runtime.ExitError. This is not a Python exception — the interpreter is killed outright, so the try/except in lambda_handler never runs and no traceback is written. It has been present since the Lambda cutover and went unnoticed because it always recovers: EventBridge invokes asynchronously, so Lambda retries the failed cycle by itself.

Diagnosed 3 Aug. The faulthandler dump deployed the day before caught the fourth abort and named it. All eight fulltext workers were inside trafilatura, three of them in htmlprocessing.prune_unwanted_nodes at the same instant. The glibc message was corrupted double-linked list.

Ruled outpsycopg2-binary's bundled OpenSSL, which had been the leading suspect. It is loaded — it appears in the extension-module list — but no thread was executing in it. Cold starts were eliminated earlier: 60 of 71 invocations are cold and only two died.

The earlier elimination of the shared parser checked the right lock and drew a conclusion about the wrong operation. lxml genuinely does lock parsers — _ParserContext.prepare() takes a per-parser lock — but that covers parsing. prune_unwanted_nodes mutates the tree afterwards, outside the lock, and because all eight threads share trafilatura's one module-level HTML_PARSER, their trees share libxml2's interned string dictionary. Concurrent mutation against a shared refcounted dict is the gap.

Fixed the same day: a module-level lock around trafilatura.extract() in utils/extract.py. The deeper finding is that no prompt can fix this. The most heavily weighted metric is measured through a proxy two other objectives are fighting over. A prediction that theta's “high magnitude even at direction 0” line would open the second path was tested and falsified — risk recall fell rather than rose.

The container deploy path cannot ship from this machine

routed around 3 Aug container path still dead

Twenty-one push attempts on 3 Aug — two deploy.ps1 runs and two direct docker push loops — all died against Docker Desktop's proxy at 192.168.65.1:3128, with broken pipe or use of closed network connection. Not credentials: re-authenticating changed nothing, and the script's “ECR login expires” hint is misleading here.

It is purely blob size. Splitting the dependency install from three layers to six pushed the 67.5 MB layer through on the next attempt. What remains is ADD file:41dd4d7f… at 433 MB — the root filesystem of public.ecr.aws/lambda/python:3.12. That is AWS's layer; it cannot be split from this side.

Resolved by removing the upload, not by fixing it. A ZIP package carries no base layer — AWS supplies the runtime — so the payload is 32.6 MB against 433 MB, under the 50 MB direct-upload limit and needing no S3 hop. The Dockerfile justified the image because dependencies "exceed Lambda's 250 MB unzipped limit"; measured, the payload is 95.6 MB. That premise was wrong.

MeasurementSizeWhat it actually was
base image rootfs433 MBAmazon Linux, CPython, the Runtime Interface Client, boto3/botocore, pip — every byte supplied free by the managed runtime
whole base filesystem537 MBbefore a line of this project exists
site-packages, our image185 MBa mix — 49 MB of AWS's own packages plus ~136 MB of ours, because pip installed into the same directory

The lesson, which is the part worth keeping. The 250 MB claim was never tested. The only figure that ever looked large was the 185 MB site-packages reading — and that was taken inside the container, so it counted AWS's 49 MB as if it were ours. A measurement taken inside the thing being justified will tend to justify it. The container was adopted to escape a limit it was never near, and in exchange it carried a 433 MB upload this network cannot deliver — which cost a day and held three commits out of production.

There was no proxy to bypass, contrary to the first diagnosis: HTTP_PROXY unset, no proxies in ~/.docker/config.json, no proxy keys in Docker Desktop's settings, 3128 absent from all of them. 192.168.65.1:3128 is Docker's own transparent gateway, exactly as the Dockerfile comment said.

GitHub Actions was proposed here and deferred. It was raised while the container push was failing, on the theory that building from a hosted runner would sidestep this machine's upload. It would have — but the ZIP removed the 433 MB upload altogether, so the problem CI was going to solve no longer exists. A deploy is now ./deploy/build-zip.ps1 -Deploy, about three minutes.

Building it now would add a second deploy path, a stored AWS credential and a release surface nobody watches, in exchange for saving three minutes on a deploy that happens roughly weekly. The version worth having later is CI, not CD: run the 217 tests on every push, and leave the deploy manual. That is the half that catches something — the tests currently run only when someone remembers.

Standingthe container path is still dead and is no longer used. deploy/build-zip.ps1 verifies rather than trusts: it aborts if any .pyd survives, if no .so exists, or if psycopg2/lxml are missing — a Windows wheel would otherwise import-fail on the first cycle rather than at build time. Watch for the ECR repository accruing images nothing pulls. Revisit Actions-as-CI once the 4 Aug scoring work lands, or sooner if a broken commit ever reaches Lambda.
